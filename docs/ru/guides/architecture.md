# Архитектура

Эта страница рассказывает, как устроена Arona и как запрос проходит через неё:
структура workspace, путь запроса, шлюз и роутер, health checking, клиент
памяти, сессии и уведомления и, наконец, осознанные ограничения и компромиссы,
которые принимает дизайн. Рабочий пример см. в
[кратком руководстве](quickstart.md), повседневные рантайм-вопросы — в
[эксплуатации](operations.md).

## Структура workspace

Репозиторий — это Cargo-workspace с тремя пакетами:

```
packages/
├── core/    # Core logic: gateway, routing, billing, auth, memory, RPC,
│            # backends, migration, entities, providers, models, registry,
│            # orchestration
├── agent/   # Remote agent (bin `_agent`): deployed on GPU machines
└── cli/     # CLI (bin `_cli`): install, deploy, serve, migrate, download
```

- `packages/core` — библиотечный крейт (`_core`). Он содержит всё, что нужно
  серверу: axum-шлюз (`gateway/`), роутер моделей (`routing/`),
  адаптеры backends (`backends/`), billing (`billing/`), auth (`auth.rs`),
  клиент памяти (`memory/`), плоскость JSON-RPC (`gateway/rpc.rs`), схему
  (`migration/`, `entity/`), метаданные моделей (`models/`, `providers/`,
  `registry/`) и оркестрацию моделей (`orchestration/`).
- `packages/agent` собирает бинарник `_agent`, который работает на GPU-узлах
  и подключается обратно через `/ws/agent` (см. [agent-cluster](agent-cluster.md)).
- `packages/cli` собирает бинарник `_cli`, используемый для операций install,
  deploy, serve, migrate и download.

В этом репозитории больше нет веб-панели: Vue-панель удалена и теперь живёт
в [shittim-chest](https://github.com/celestia-island/shittim-chest) (chest #291),
который общается с Arona через JSON-RPC-поверхность. Сама Arona — чистый
backend (см. [обзор](./README.md)).

## Путь запроса

Точка входа — axum-роутер, собранный в `GatewayServer::app`
(`packages/core/src/gateway/server.rs`). Его таблица маршрутов (server.rs:128-163)
покрывает OpenAI-совместимую REST-поверхность (`/v1/chat/completions`,
`/v1/embeddings`, `/v1/models`, `/v1/health`), генерацию видео, JSON-RPC-endpoint
`/api/rpc` (POST + WebSocket upgrade), SSE-sidecar `/api/rpc/events`, плоскость
управления агентами `/ws/agent`, Swagger UI на `/docs` и admin-endpoints
управления backends/алиасами.

Роутер обёрнут в небольшой стек слоёв (server.rs:158-162):

1. Auth-менеджеры как `Extension`, чтобы per-обработчиковые экстракторы могли
   до них добраться.
2. Слой request-id, который переиспользует входящий заголовок `X-Request-ID`
   или генерирует его, открывая его обработчикам и логам
   (`gateway/request_id.rs`).
3. Лимит тела запроса 1 МБ (`RequestBodyLimitLayer`).
4. Разрешительный CORS-слой (`*` origin, `*` headers).

Поскольку axum применяет слои снизу вверх, CORS-слой оказывается самым
внешним.

Каждый обработчик `/v1/*` затем проходит через один и тот же скелет:

1. **Извлечение auth** — `ApiKeyAuth` для endpoints только с ключом
   (`/v1/chat/completions`, `/v1/embeddings`, видео) и `ApiKeyOrJwt` для
   `GET /v1/models`, который обязан принимать и API keys, и сессионные JWT
   (`gateway/middleware.rs`). Экстрактор разрешает ключ/JWT в email
   пользователя, префикс ключа, ключ rate limit (SHA-256-хеш API key или
   метку `u:<email>` для JWT, чтобы ротирующиеся tokens не сбрасывали окно)
   и опциональный охват проекта.
2. **Billing-гейты** — `enforce_billing_gates` (server.rs:492-539) отклоняет
   запрос с HTTP 429 + `Retry-After`, когда превышена месячная квота tier
   или минутный rate limit пользователя. Сбои БД fail open: billing —
   best-effort, никогда не жёсткая зависимость обслуживания чата.
3. **Recall памяти** (пути чата) — если клиент памяти настроен и запрос его
   просит, релевантные долговременные воспоминания инъецируются как системная
   секция (см. [Memory client](#memory-client) ниже). Сбой никогда не блокирует
   чат; итоговое состояние отражается в заголовке `X-Arona-Memory`.
4. **Сохранение диалога** — опциональный `conversation_id` проверяется на
   владение, и ход пользователя сохраняется в момент отправки.
5. **Диспетчеризация шлюза** — запрос передаётся `Gateway`, который разрешает
   backend, подрезает контекст и вызывает трейт backend.
6. **Запись usage** — возвращённый (или терминальный для потока) usage
   записывается и сохраняется через `UsageTracker` под префиксом ключа.

Сам `Gateway` живёт в `AppState` как `Arc<Gateway>` — внешнего мьютекса нет;
внутренняя мутабельность не даёт параллельным вызовам чата/embeddings/stream
когда-либо держать блокировку поперёк HTTP-кругооборота upstream
(`gateway/mod.rs:29-53`).

## Gateway и роутер

`Gateway` (`packages/core/src/gateway/mod.rs`) владеет:

- **Состоянием роутера** — списком backends и алиасов, защищённым
  `tokio::sync::RwLock`. Разрешение на чтение занимает borrow поперёк await'ов;
  мутации (register/remove/alias) берут короткую write-блокировку и никогда
  не держат её поперёк вызова upstream.
- **Счётчиком запросов** (`AtomicU64`) и `start_time`, используемыми
  `system.status` и health-endpoint'ами.
- **Картой развёртываний** (`model_id → backend name`) для развёрнутых
  агентом моделей. `register_agent_backend` строит `ExternalApiBackend`
  с именем `agent-{model_id}` и вставляет его в роутер; повторная регистрация
  той же модели заменяет предыдущий backend, а `unregister_agent_backend`
  удаляет его при кадре `stop_result` (см. [agent-cluster](agent-cluster.md)).

Разрешение backend происходит в `Router` (`packages/core/src/routing/mod.rs`):

1. **Разрешение алиаса** — настроенный алиас переписывается в свою цель.
2. **Привязка сессии** — когда присутствует `conversation_id`, роутер
   проверяет map со слабыми ссылками, которая закрепляет диалог за backend,
   обслужившим его первым. Слабые ссылки держат map в живых только пока
   backend зарегистрирован или в полёте, поэтому удалённые backends исчезают
   без дрейфа индексов. Сработавший circuit breaker или unhealthy
   закреплённый backend деградируют в свежий выбор, который перепривязывает
   диалог.
3. **Фильтрация кандидатов** — опциональная подсказка `provider` фильтрует
   по имени/виду backend; кандидаты должны быть healthy *и* иметь открытый
   circuit breaker, а также перечислять запрошенную модель. Id моделей
   совпадают точно или через конвенцию суффикса `:latest` (голый запрос
   `nomic-embed-text` совпадает с перечисленным `nomic-embed-text:latest`).
4. **Выбор наименее загруженного** — выжившие кандидаты сортируются по своему
   счётчику попаданий, и выбирается наименее загруженный; привязка диалога
   (если есть) записывается в тот же момент.

Перед вызовом backend `RequestPipeline::transform`
(`packages/core/src/pipeline.rs:422+`) подрезает список сообщений до
`max_context_length` backend: системные сообщения сохраняются полностью,
не-системные сохраняются от новых к старым, пока помещаются, а одно
непомерно большое сообщение жёстко обрезается по символам (эвристический
счётчик tokens не может обрезать точно по tokens). Затем вызов идёт через
трейт `InferenceBackend`; успехи и сбои записываются обратно в per-backend
circuit breaker роутера (3 сбоя, 30 с восстановления, 1 half-open вызов —
routing/mod.rs:57-64).

## Health-checker и probing

`run_health_checks` (`packages/core/src/gateway/health_checker.rs`) работает
как фоновая задача, порождённая при старте (run.rs:135-150), и пробирует
каждый зарегистрированный backend раз в 60-секундный интервал. Важны две
детали:

- Список backends **заново забирается на каждом раунде** через async-замыкание
  fetcher'а, поэтому backends, зарегистрированные после старта (например, через
  admin API), подхватываются без перезапуска.
- Первый раунд выполняется сразу, до истечения первого интервала, поэтому
  состояние health устанавливается, как только процесс стартует.

`probe_backend` — единственный путь кода пробы. Он переиспользуется
разовыми **пробами при регистрации**: после того как администратор
регистрирует backend (server.rs:688-693) или сохранённый backend
восстанавливается при загрузке (run.rs:122-127), fire-and-forget-проба
переводит backend в healthy в течение ~1–2 с, вместо того чтобы оставаться
fail-closed до следующего 60-секундного раунда. Именно поэтому список моделей
свежезарегистрированного external backend почти сразу появляется
в `GET /v1/models`.

Сама проба — это лёгкий вызов backend (например, external backend бьёт
в `/v1/models` с 2-секундным таймаутом пробы); результат кэшируется
в backend, и маршрутизация выбирает только backends, чей кэшированный health
равен `Healthy` (плюс открытый circuit breaker).

## Memory client

Клиент памяти (`packages/core/src/memory/mod.rs`) конструируется из
конфигурации окружения при старте сервера (server.rs:95-97): когда заданы
`ARONA_MEMORY_URL` и `ARONA_MEMORY_TOKEN`, чат-запросы обращаются к сервису
памяти entelecheia Philia через JSON-RPC WebSocket, и `recall_and_inject`
добавляет в начало исходящего контекста релевантные воспоминания как
системную секцию (`## Relevant Long-Term Memories`). Завершённые ходы
записываются обратно как эпизоды через `writeback_dialogue` — работа
fire-and-forget, порождённая после сохранения ответа ассистента, поэтому
сбои памяти никогда не блокируют и не замедляют путь ответа чата.
`ARONA_MEMORY_WRITEBACK` (по умолчанию включён) переключает writeback.
Полную картину см. в [memory-gateway](memory-gateway.md).

Каждый ответ чата несёт заголовок `X-Arona-Memory` с одним из трёх состояний:
`enabled` (recall отработал и инъецировал), `disabled` (не настроено или
запрос передал `memory: false`) или `offline` (настроено, но сервис был
недостижим).

## Сессии и уведомления

`AppState` держит `plana` `SessionManager` (`state.sessions`).
Streaming-RPC вроде `chat.send` создают id сессии (`gateway/rpc.rs:1701`)
и выталкивают уведомления — tokens `chat.stream`, прогресс развёртывания
`models.progress`, `realtime.event` — в канал этой сессии. Клиенты потребляют
их из SSE-sidecar `GET /api/rpc/events?session=<id>` (server.rs:191-200);
формат уведомлений и предостережение об окне до подписки см. в
[events](../api/events.md).

Канал сессии также используется для RPC-вызовов запрос/ответ: когда клиент
отправляет заголовок `x-session-id` на `POST /api/rpc`, сервер также
выталкивает результат в этот канал сессии (server.rs:184-188, rpc.rs:128-144),
поэтому клиент может мультиплексировать RPC-ответ в уже открытый SSE-поток.

## Ограничения и дизайн-компромиссы

Дизайн осознанно принимает ряд ограничений; знайте их перед использованием
в production:

- **Лимит тела запроса 1 МБ** — более крупные тела отклоняются слоем;
  если вам нужны вызовы с большим контекстом, это первое, что стоит
  настраивать.
- **CORS `*`** — шлюз отвечает на кросс-ориджин вызовы откуда угодно.
  Для API это нормально, но если вы открываете его за пределы доверенных
  клиентов, поставьте перед ним proxy, применяющий вашу собственную
  CORS-политику.
- **Fail-open billing** — принудительное применение квот/rate limit деградирует
  до разрешения запроса, когда БД недоступна. Billing — это учёт, а не
  контроль доступа.
- **Нет общего таймаута на SSE-потоках** — streaming-вызовы не несут общего
  дедлайна (длинные генерации допустимы); обнаружение зависаний полагается
  на 120-секундный per-read idle таймаут (`backends/external.rs:24-31`).
  Non-streaming вызовы получают общий дедлайн 600 с.
- **Usage по оценке tokenizer** — backends, которые никогда не сообщают
  usage (ollama, ws_engine), тарифицируются по локальной CJK-осведомлённой
  оценке tokenizer, записываемой как есть (см. [billing-usage](billing-usage.md)).
- **Окна rate limit и отзыв в памяти** — per-key скользящее окно
  и множество отозванных ключей живут в памяти процесса (`auth.rs`), поэтому
  перезапуск сбрасывает их. Лимитер на уровне auth ограничивает запросы
  на ключ на окно; лимитер billing-tier опирается на БД (см.
  [auth-security](auth-security.md) и [billing-usage](billing-usage.md)).
- **`/ws/agent` не аутентифицирован** — плоскость управления агентами
  принимает любой WebSocket, говорящий на протоколе register/heartbeat.
  Это безопасно только в сети, которой вы управляете.
- **Нет TLS на шлюзе** — сервер слушает обычный HTTP; терминируйте TLS
  впереди (reverse proxy) в любом развёртывании, пересекающем границу сети.
  См. [deployment](deployment.md).

С другой стороны, сервер выполняет graceful shutdown: он устанавливает
обработчики Ctrl+C и SIGTERM, логирует «draining connections» и даёт
выполняющимся запросам завершиться до выхода процесса (`gateway/run.rs:14-38`
и проводка `with_graceful_shutdown` в run.rs:154-159).
