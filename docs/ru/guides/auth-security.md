# Аутентификация и безопасность

Arona аутентифицирует вызывающих по двум трекам: **JWT-tokens сессий** для
интерактивных клиентов (чат + admin UI, RPC-вызовы) и **API keys**
(`arona-…`) для программного OpenAI-совместимого трафика. Отдельный admin
token защищает административные поверхности. Эта страница документирует
механику, модель безопасности и известные низкорисковые остатки из аудита
безопасности.

## JWT-сессии

Сессии используют пары JWT access/refresh, выдаваемые менеджером tokens
`kirino_session`:

- **TTL access-token: 900 секунд (15 минут).**
- **TTL refresh-token: 604 800 секунд (7 дней).**

Access-tokens аутентифицируют плоскость JSON-RPC (`/api/rpc`) и
`GET /v1/models`; SSE-sidecar (`/api/rpc/events`) привязан к своему id
сессии — это capability, выпущенная во время аутентифицированных RPC-вызовов,
а не bearer-учётные данные. Endpoints `/v1/chat/completions`, `/v1/embeddings`
и `/v1/video/*` требуют **API key** (JWT там не принимается).
Access-tokens короткоживущие, поэтому украденный token можно использовать
лишь недолго. Refresh-tokens обмениваются на свежие пары через `auth.refresh`.

Refresh использует **ротацию token семейств**: потребление refresh-token
инвалидирует его и выдаёт новый, а повторное использование потреблённого
refresh-token отзывает всё семейство — `auth.refresh` отвечает `AUTH_ERROR`
с сообщением `Refresh token reused` (лежащая в основе ошибка — `TokenReused`,
«refresh token has been reused — token family revoked»), и аккаунт должен войти
заново. Отзыв семейства **в памяти** (множество `revoked_families`):
перезапуск сервера очищает его, поэтому защита best-effort между
перезапусками (состояние сессий пользователей не переживает перезапуск).

Секрет подписи берётся из переменной окружения `JWT_SECRET`. Вне
`MOCK_MODE=1` сервер **отказывается запускаться**, если `JWT_SECRET` не задан
или всё ещё равен встроенному development-секрету, поэтому production-инстанс
никогда не сможет случайно выдать tokens, подписанные публичной константой.
Используйте сильный случайный секрет и никогда не коммитьте его.

## API keys

API keys — это машинные учётные данные для OpenAI-совместимой поверхности:

- **Формат:** `arona-{uuid}`.
- **Хранение:** в таблице `api_keys` хранится только **SHA-256-хеш** ключа —
  открытый текст возвращается ровно один раз, в ответе `keys.create`,
  и впоследствии его невозможно восстановить.
- **Префикс ключа:** первые 8 символов (`key_prefix`) хранятся в открытом виде
  для отображения и атрибуции usage; UI показывает маскированную форму вида
  `arona-XXXX…abcd`.
- **Отзыв:** поиск ключа соединяется с `api_keys.is_active = TRUE`, поэтому
  отозванный ключ перестаёт валидироваться немедленно — нет TTL кэша,
  который нужно переждать.

## Уровни администратора

Существует три отдельных уровня администратора, у каждого свои учётные данные:

1. **Маршруты `/api/admin/*`** — управление backends и алиасами
   (`POST/GET/DELETE /api/admin/backends`, `POST/GET/DELETE /api/admin/aliases`)
   требует заголовок `Authorization: Bearer ARONA_ADMIN_TOKEN`. Когда
   `ARONA_ADMIN_TOKEN` не задан, `check_admin` всегда завершается неудачей,
   и каждый admin-маршрут возвращает **401 "Admin access required"** — вся
   поверхность управления отключена, а не открыта.

2. **RPC-методы `agents.*` и `engine.invoke`** — кластер агентов и
   плоскость управления движками требуют JWT, у аккаунта которого
   `users.is_admin = true`. Аутентифицированный не-администратор отклоняется
   с определяемым реализацией кодом **-32007 (`ADMIN_REQUIRED`)** плюс
   подсказка, специфичная для метода (например, `agents.deploy starts model
   deployments on GPU nodes`); **неаутентифицированный** вызывающий получает
   стандартный **-32005 (`AUTH_ERROR`)**, чтобы сервер не раскрывал, что
   метод вообще привилегированный.

3. **RPC-методы `billing.plan.set` и `billing.video.pricing.set`** —
   мутации billing требуют тот же Bearer `ARONA_ADMIN_TOKEN`, что и admin
   HTTP-маршруты; без него они возвращают `AUTH_ERROR` "Admin access required".

**Первый зарегистрированный пользователь становится администратором**
(`users.is_admin = true`). Каждая последующая регистрация — обычный
пользователь, и регистрация открыта только пока `ARONA_REGISTRATION_OPEN`
имеет truthy-значение.

## Политика паролей

Пароли должны удовлетворять **обоим** правилам (проверяются при регистрации
и на любом пути смены пароля):

- не менее **8 символов**, и
- не менее **3 из 4 категорий символов**: заглавные, строчные, цифры,
  спецсимволы.

## Ограничение частоты запросов

Ограничение частоты работает на двух независимых треках; любой из них может
отклонить запрос с **429**:

### 1. Скользящее окно в памяти (по идентичности)

Каждый аутентифицированный запрос `/v1` проходит через лимитер со скользящим
окном в памяти, привязанный к идентичности вызывающего:

- **Вызовы с API key** привязаны к **SHA-256-хешу** ключа;
- **JWT-вызовы** привязаны к `u:<email>` — JWT ротируются каждые 15 минут,
  поэтому привязка окна к экземпляру token молча сбрасывала бы его при
  каждом refresh.

Бюджет по умолчанию — **60 запросов в минуту**, переопределяется через
`ARONA_API_RATE_LIMIT_RPM` (увеличьте для агентских пайплайнов, которые
рассылают много параллельных LLM-вызовов). Значение **0 блокирует каждый
запрос**.

### 2. Лимит tier (на ключ, из базы данных)

Billing tiers несут per-ключевой `rate_limit_rpm`. Проверка считает строки
`usage_records` для префикса ключа в **последних 60 секундах** (usage
сохраняется после каждого ответа, поэтому окно отстаёт максимум на один
выполняющийся запрос; сбои БД fail open). Предустановленный **free tier —
10 RPM**; tiers pro/enterprise поднимают потолок. Ежемесячное квотирование
использует тот же путь отклонения.

### Ограничение частоты запросов при входе

Перебор учётных данных ограничивается на login-endpoint: **5 неудачных попыток
за 5-минутное окно на email** и **20 за 5-минутное окно на IP**, после чего
следует 15-минутная блокировка.

### `Retry-After`

Каждый ответ 429 несёт заголовок `Retry-After`, чтобы OpenAI-совместимые
клиенты отступали, а не долбили endpoint: квотные отклонения устанавливают его
в **секунды до конца месяца**; отклонения по rate limit устанавливают его
в **60**. Модель квот см. в [Billing & Usage](billing-usage.md).

## Заметки о модели безопасности

- **CORS разрешает любой origin** (`allow_origin(Any)`) — Arona это backend,
  потребляемый множеством сторонних и собственных клиентов; если ваш
  деплоймент должен ограничивать origins, поставьте перед ним reverse proxy,
  который принудительно применяет CORS.
- **Тела запросов ограничены 1 МБ** (`RequestBodyLimitLayer`), ограничивая
  использование памяти на шлюзе.
- **Шлюз не терминирует TLS** — он слушает обычный HTTP. Поставьте его за
  reverse proxy (см. [Развёртывание](deployment.md)), который терминирует
  HTTPS.
- **Секреты приходят только из окружения**: `ARONA_ADMIN_TOKEN`
  и `JWT_SECRET` читаются из переменных окружения и должны быть сильными
  случайными значениями, которые никогда не коммитятся в репозиторий.
- Адрес привязки сервера по умолчанию — `0.0.0.0`; ограничьте доступность
  на сетевом уровне.

## Известные низкорисковые остатки (из аудита)

Ниже задокументировано как есть; это намеренно или принято пока, но о них
стоит знать, когда вы открываете инстанс за пределы доверенной сети:

- **`providers.list` публичен**, тогда как `providers.add` / `providers.update` /
  `providers.remove` / `providers.test` требуют JWT. Публичный путь чтения
  раскрывает каталог provider'ов, но ничего секретного.
- **`/ws/agent` — неаутентифицированная плоскость управления**: GPU-агенты
  подключаются без учётных данных и саморегистрируются (кадры `register` /
  `heartbeat` / command-result). Любой, кто может достучаться до
  WebSocket-порта, может зарегистрировать фейкового агента. Эксплуатационные
  компромиссы см. в [Agent Cluster](agent-cluster.md).
- **`memory.delete` только с JWT, без проверки владения**: любой
  аутентифицированный пользователь может удалить узел памяти по `node_id`.
  Для удаления памяти нужно быть залогиненным, но не обязательно владеть
  узлом.
