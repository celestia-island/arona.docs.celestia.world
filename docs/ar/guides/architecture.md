# البنية

تستعرض هذه الصفحة كيف يُنظَّم أرونا وكيف يتدفق الطلب عبره: تخطيط مساحة العمل،
مسار الطلب، الـ gateway والموجّه (router)، فحص الصحة، عميل الذاكرة، الجلسات
والإشعارات، وأخيرًا الحدود والمقايضات المتعمدة التي يقبلها التصميم. انظر
[البدء السريع](quickstart.md) لمثال عملي و
[العمليات](operations.md) لاهتمامات التشغيل اليومية.

## تخطيط مساحة العمل

المستودع هو Cargo workspace بثلاث حزم:

```
packages/
├── core/    # Core logic: gateway, routing, billing, auth, memory, RPC,
│            # backends, migration, entities, providers, models, registry,
│            # orchestration
├── agent/   # Remote agent (bin `_agent`): deployed on GPU machines
└── cli/     # CLI (bin `_cli`): install, deploy, serve, migrate, download
```

- `packages/core` هو crate المكتبة (`_core`). يحتوي كل ما يحتاجه الخادم:
  الـ gateway الخاص بـ axum (`gateway/`)، وموجّه النماذج (`routing/`)،
  ومهايئات الـ backends (`backends/`)، والفوترة (`billing/`)، والمصادقة
  (`auth.rs`)، وعميل الذاكرة (`memory/`)، ومستوى JSON-RPC (`gateway/rpc.rs`)،
  والمخطط (`migration/`، `entity/`)، وبيانات النماذج الوصفية (`models/`،
  `providers/`، `registry/`)، وتنظيم النماذج (`orchestration/`).
- يبني `packages/agent` الثنائي `_agent` الذي يعمل على عقد GPU ويتصل بالخلف
  عبر `/ws/agent` (انظر [مجموعة الوكلاء](agent-cluster.md)).
- يبني `packages/cli` الثنائي `_cli` المستخدم في عمليات التثبيت والنشر
  والتشغيل والترحيل والتنزيل.

لم يعد هناك لوحة تحكم ويب في هذا المستودع: أُزيلت لوحة Vue وتعيش الآن في
[shittim-chest](https://github.com/celestia-island/shittim-chest) (chest #291)،
الذي يتواصل مع أرونا عبر سطح JSON-RPC. أرونا نفسه backend خالص
(انظر [النظرة العامة](./README.md)).

## مسار الطلب

نقطة الدخول هي موجّه axum المُجمَّع في `GatewayServer::app`
(`packages/core/src/gateway/server.rs`). يغطي جدول مساراته (server.rs:128-163)
سطح REST المتوافق مع OpenAI (`/v1/chat/completions`، `/v1/embeddings`،
`/v1/models`، `/v1/health`)، وتوليد الفيديو، ونقطة نهاية JSON-RPC
`/api/rpc` (POST + ترقية WebSocket)، والمرافق الجانبي SSE `/api/rpc/events`،
ومستوى التحكم بالوكلاء `/ws/agent`، وواجهة Swagger UI عند `/docs`، ونقاط
نهاية إدارة الـ backends والاسم المستعار (alias).

يُغلَّف الموجّه في رزمة صغيرة من الطبقات (server.rs:158-162):

1. مديرو المصادقة كـ `Extension` حتى تصل إليهم مستخرجات كل معالج.
2. طبقة معرف الطلب تعيد استخدام ترويسة `X-Request-ID` الواردة أو تولّد
   واحدة، مكشوفة للمعالجات والسجلات (`gateway/request_id.rs`).
3. حد 1 MB لحجم جسم الطلب (`RequestBodyLimitLayer`).
4. طبقة CORS متساهلة (أصل `*`، ترويسات `*`).

ولأن axum يطبق الطبقات من الأسفل إلى الأعلى، تكون طبقة CORS في أقصى الخارج.

يمر كل معالج `/v1/*` بعد ذلك عبر الهيكل نفسه:

1. **استخراج المصادقة** — `ApiKeyAuth` لنقاط النهاية الخاصة بالمفتاح فقط
   (`/v1/chat/completions`، `/v1/embeddings`، الفيديو) و`ApiKeyOrJwt` لمسار
   `GET /v1/models`، الذي يجب أن يقبل كلًا من API keys وJWTs الجلسات
   (`gateway/middleware.rs`). يحل المستخرِج المفتاح/JWT إلى بريد المستخدم
   الإلكتروني، وبادئة المفتاح، ومفتاح حد المعدل (هاش SHA-256 للمفتاح، أو
   وسم `u:<email>` للـ JWTs كي لا تُصفَّر النافذة عند تدوير الـ tokens)
   ونطاق مشروع اختياري.
2. **بوابات الفوترة** — ترفض `enforce_billing_gates` (server.rs:492-539)
   الطلب برمز HTTP 429 + `Retry-After` عندما تُتجاوز الحصة الشهرية لمستوى
   المستخدم أو حد المعدل لكل دقيقة. فشل قاعدة البيانات يفتح الباب (fail
   open): الفوترة جهدٌ أفضل (best-effort)، وليست أبدًا اعتمادًا صارمًا
   لخدمة الدردشة.
3. **استرجاع الذاكرة** (مسارات الدردشة) — إذا كان عميل الذاكرة مهيأً وطلب
   الطلب ذلك، تُحقن الذكريات طويلة المدى ذات الصلة كقسم نظام
   (انظر [عميل الذاكرة](#memory-client) أدناه). لا يحجب الفشل الدردشة أبدًا؛
   وتنعكس الحالة الناتجة في ترويسة `X-Arona-Memory`.
4. **استمرار المحادثة** — يخضع `conversation_id` الاختياري لفحص الملكية،
   ويُثبَّت دور المستخدم وقت الإرسال.
5. **إرسال الـ Gateway** — يُسلَّم الطلب إلى `Gateway`، الذي يحل backend،
   ويقلّص السياق، ويستدعي trait الـ backend.
6. **تسجيل الاستخدام** — يُسجَّل الاستخدام المعاد (أو النهائي للبث) ويُثبَّت
   عبر `UsageTracker` تحت بادئة المفتاح.

يعيش `Gateway` نفسه في `AppState` كـ `Arc<Gateway>` — لا يوجد mutex خارجي؛
تضمن القابلية للتغيير الداخلية (interior mutability) ألا تمسك استدعاءات
الدردشة/التضمينات/البث المتزامنة قفلًا عبر رحلة HTTP ذهابًا وإيابًا إلى
الـ upstream (`gateway/mod.rs:29-53`).

## الـ Gateway والموجّه

يملك `Gateway` (`packages/core/src/gateway/mod.rs`):

- **حالة الموجّه** — قائمة الـ backends والاسم المستعار (aliases)، محمية
  بـ `tokio::sync::RwLock`. يقترض تحليل جانب القراءة عبر نقاط الانتظار
  (awaits)؛ وتأخذ الطفرات (تسجيل/إزالة/اسم مستعار) قفل كتابة قصيرًا ولا
  تمسكه أبدًا عبر استدعاء upstream.
- **عداد طلبات** (`AtomicU64`) و`start_time` يستخدمهما `system.status` ونقاط
  نهاية الصحة.
- **خريطة عمليات نشر** (`model_id → backend name`) للنماذج المنشورة بواسطة
  الوكلاء. يبني `register_agent_backend` `ExternalApiBackend` باسم
  `agent-{model_id}` ويدرجه في الموجّه؛ وإعادة تسجيل النموذج نفسه تستبدل
  الـ backend السابق، ويزيله `unregister_agent_backend` عند إطار
  `stop_result` (انظر [مجموعة الوكلاء](agent-cluster.md)).

يتم حل الـ backend في `Router` (`packages/core/src/routing/mod.rs`):

1. **حل الاسم المستعار** — يُعاد كتابة الاسم المستعار المهيأ إلى هدفه.
2. **الارتباط بالجلسة** — عند وجود `conversation_id`، يفحص الموجّه خريطة
   مراجع ضعيفة (weak references) تثبّت المحادثة إلى الـ backend الذي خدمها
   أول مرة. تُبقي المراجع الضعيفة الخريطة حية فقط ما دام الـ backend مسجلًا
   أو قيد التنفيذ، فتختفي الـ backends المزالة دون انحراف في الفهارس. أي
   قاطع دائرة (circuit breaker) مفعّل أو backend مثبّت غير سليم يتدهور إلى
   اختيار جديد، يعيد ربط المحادثة.
3. **تصفية المرشحين** — تلميح `provider` اختياري يصفّي حسب اسم/نوع الـ
   backend؛ يجب أن يكون المرشحون سليمين *و* أن يكون قاطع الدائرة مفتوحًا
   لديهم، وأن يُدرجوا النموذج المطلوب. تُطابَق معرفات النماذج تمامًا أو عبر
   اصطلاح اللاحقة `:latest` (طلب `nomic-embed-text` العادي يطابق المُدرج
   `nomic-embed-text:latest`).
4. **اختيار الأقل تحميلًا** — تُرتَّب المرشحات الباقية حسب عدّاد الزيارات
   ويُختار الأقل تحميلًا؛ ويُسجَّل تثبيت المحادثة (إن وُجد) في الوقت نفسه.

قبل استدعاء الـ backend، يقلّص `RequestPipeline::transform`
(`packages/core/src/pipeline.rs:422+`) قائمة الرسائل إلى
`max_context_length` الخاص بالـ backend: تُحفظ رسائل النظام كاملة، وتُحفظ
رسائل غير النظام الأحدث أولًا ما دامت تتسع، ويُبتَر أي رسالة واحدة ضخمة
بترميز الأحرف (لا يستطيع عدّاد الـ tokens الاستدلالي البتر بدقة على مستوى
الـ token). يمر الاستدعاء بعد ذلك عبر trait `InferenceBackend`؛ وتُسجَّل
النجاحات والإخفاقات في قاطع الدائرة الخاص بكل backend في الموجّه
(3 إخفاقات، استرداد خلال 30 ثانية، استدعاء واحد نصف مفتوح —
routing/mod.rs:57-64).

## فاحص الصحة والاستطلاع (probing)

يعمل `run_health_checks` (`packages/core/src/gateway/health_checker.rs`) كمهمة
خلفية تُطلق عند بدء التشغيل (run.rs:135-150) ويستطلع كل backend مسجل مرة
واحدة كل فاصل زمني قدره 60 ثانية. هناك تفصيلان مهمان:

- **تُجلب قائمة الـ backends من جديد في كل جولة** عبر إغلاق جالب غير متزامن،
  فتُلتقط الـ backends المسجلة بعد بدء التشغيل (مثلًا عبر واجهة الإدارة)
  دون إعادة تشغيل.
- تعمل الجولة الأولى فورًا، قبل انقضاء أول فاصل زمني، فيُثبَّت وضع الصحة
  بمجرد بدء العملية.

`probe_backend` هو مسار كود الاستطلاع الوحيد. يُعاد استخدامه في **استطلاعات
وقت التسجيل** لمرة واحدة: بعد أن يسجّل مسؤول backend (server.rs:688-693) أو
يُستعاد backend مثبّت عند الإقلاع (run.rs:122-127)، يقلب استطلاع يُطلق
ويُنسى (fire-and-forget) الـ backend إلى سليم خلال نحو 1–2 ثانية بدل البقاء
مغلقًا عند الفشل حتى الجولة التالية بعد 60 ثانية. هذا ما يجعل قائمة نماذج
backend خارجي مسجّل حديثًا تظهر في `GET /v1/models` فورًا تقريبًا.

الاستطلاع نفسه استدعاء backend خفيف (مثلًا يضرب الـ backend الخارجي
`/v1/models` بمهلة استطلاع قدرها 2 ثانية)؛ تُخزَّن النتيجة في الـ backend
مؤقتًا، ولا يختار التوجيه إلا الـ backends التي تكون صحتها المخزنة `Healthy`
(مع قاطع دائرة مفتوح).

## عميل الذاكرة

يُبنى عميل الذاكرة (`packages/core/src/memory/mod.rs`) من إعداد البيئة عند
بدء تشغيل الخادم (server.rs:95-97): عندما يُضبط `ARONA_MEMORY_URL` و
`ARONA_MEMORY_TOKEN`، تستعلم طلبات الدردشة خدمة ذاكرة entelecheia Philia عبر
JSON-RPC WebSocket، وتُدرج `recall_and_inject` الذكريات ذات الصلة كقسم نظام
(`## Relevant Long-Term Memories`) في السياق الصادر. تُكتب الأدوار المكتملة
بالخلف كحلقات (episodes) عبر `writeback_dialogue` — عمل يُطلق ويُنسى بعد
تثبيت رد المساعد، فلا تحجب إخفاقات الذاكرة مسار استجابة الدردشة أو تبطئه
أبدًا. يبدّل `ARONA_MEMORY_WRITEBACK` (مفعّل افتراضيًا) إعادة الكتابة.
انظر [بوابة الذاكرة](memory-gateway.md) للصورة الكاملة.

تحمل كل استجابة دردشة ترويسة `X-Arona-Memory` بواحدة من ثلاث حالات:
`enabled` (تم الاسترجاع والحقن)، أو `disabled` (غير مهيأ أو مرر الطلب
`memory: false`)، أو `offline` (مهيأ لكن الخدمة كانت غير قابلة للوصول).

## الجلسات والإشعارات

يحمل `AppState` `SessionManager` من `plana` (`state.sessions`). تنشئ استدعاءات
RPC المتدفقة مثل `chat.send` معرف جلسة (`gateway/rpc.rs:1701`) وتدفع
الإشعارات — tokens الخاصة بـ `chat.stream`، وتقدم نشر `models.progress`،
و`realtime.event` — إلى قناة تلك الجلسة. يستهلكها العملاء من المرافق الجانبي
SSE `GET /api/rpc/events?session=<id>` (server.rs:191-200)؛ انظر
[الأحداث والإشعارات](../api/events.md) لصيغة الإشعار ونافذة ما قبل الاشتراك
وتحذيراتها.

تُستخدم قناة الجلسة أيضًا لاستدعاءات RPC من نوع طلب/استجابة: عندما يرسل
العميل ترويسة `x-session-id` على `POST /api/rpc`، يدفع الخادم النتيجة إلى
قناة تلك الجلسة أيضًا (server.rs:184-188, rpc.rs:128-144)، فيستطيع العميل
تعدد إرسال استجابة RPC على بث SSE مفتوح أصلًا.

## الحدود والمقايضات التصميمية

يقبل التصميم عمدًا عددًا من الحدود؛ اعرفها قبل الاستخدام الإنتاجي:

- **حد جسم الطلب 1 MB** — ترفض الطبقة الأجسام الأكبر؛ إذا احتجت استدعاءات
  بسياق ضخم، فهذا أول شيء تضبطه.
- **CORS `*`** — يجيب الـ gateway عن استدعاءات عبر الأصول من أي مكان. أمر
  جيد لواجهة برمجة، لكن إذا كشفتَه لما يتجاوز العملاء الموثوقين، ضع أمامه
  وكيلًا (proxy) يفرض سياسة CORS الخاصة بك.
- **الفوترة مفتوحة عند الفشل (fail-open)** — يتدهور فرض الحصة/حد المعدل إلى
  السماح بالطلب عندما تكون قاعدة البيانات غير متاحة. الفوترة قياس، وليست
  تحكمًا بالوصول.
- **لا مهلة إجمالية على بث SSE** — لا تحمل الاستدعاءات المتدفقة موعدًا
  نهائيًا إجماليًا (التوليدات الطويلة مشروعة)؛ يعتمد كشف التعليق على مهلة
  خمول قدرها 120 ثانية لكل قراءة (`backends/external.rs:24-31`). تحصل
  الاستدعاءات غير المتدفقة على مهلة إجمالية قدرها 600 ثانية.
- **استخدام بتقدير الـ tokenizer** — تُفوتر الـ backends التي لا تبلغ عن
  الاستخدام أبدًا (ollama، ws_engine) من تقدير tokenizer محلي واعٍ باللغة
  الصينية (CJK)، ويُسجَّل كما هو (انظر [الفوترة والاستخدام](billing-usage.md)).
- **نوافذ حد المعدل والإبطال في الذاكرة** — تعيش النافذة المنزلقة لكل مفتاح
  ومجموعة المفاتيح الملغاة في ذاكرة العملية (`auth.rs`)، فيعيد التشغيل
  تصفيرها. يحدّ المقيِّد على مستوى المصادقة الطلبات لكل مفتاح في كل نافذة؛
  أما المقيِّد على مستوى الـ billing tier فمعتمد على قاعدة البيانات (انظر
  [أمان المصادقة](auth-security.md) و[الفوترة والاستخدام](billing-usage.md)).
- **`/ws/agent` غير مصادَق** — يقبل مستوى التحكم بالوكلاء أي WebSocket يتحدث
  بروتوكول التسجيل/نبض القلب. لا يكون آمنًا إلا على شبكة تتحكم بها.
- **لا TLS على الـ gateway** — يرتبط الخادم بـ HTTP صريح؛ أنهِ TLS في المقدمة
  (وكيل عكسي) في أي نشر يعبر حدود شبكة. انظر [النشر](deployment.md).

على الجانب اللطيف، ينفذ الخادم إيقافًا لطيفًا (graceful shutdown): يثبّت
معالجي Ctrl+C وSIGTERM، ويسجّل "draining connections"، ويترك الطلبات قيد
التنفيذ تكتمل قبل خروج العملية (`gateway/run.rs:14-38`، وتوصيل
`with_graceful_shutdown` عند run.rs:154-159).
